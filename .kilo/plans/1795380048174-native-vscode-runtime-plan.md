# Native VS Code Runtime Without the CLI

## Goal and Decisions

Replace the VS Code extension's local `kilo serve` process and bundled CLI with an extension-host JavaScript runtime. The final VSIX must contain zero bytes of the `kilo` executable, must not launch or require a local Kilo backend, and must add no package dependencies. Use existing VS Code/Node APIs, existing workspace packages, and direct network APIs where needed. Minimize final VSIX size and report compressed and uncompressed sizes by component.

Preserve VS Code product behavior, including the agent loop, sessions, tools, permissions/questions, built-in provider protocols and auth, Kilo cloud integrations, MCP (local and remote), agents/skills, indexing/search, browser/LSP integrations, and Agent Manager/worktrees. CLI/TUI-only interfaces and command surfaces are out of scope.

Explicit scope decisions:

- Hand-code adapters for all currently built-in providers and auth flows, plus custom OpenAI-compatible endpoints. Do not support arbitrary dynamically installed provider npm packages.
- Preserve MCP and marketplace support for supported content, but do not execute arbitrary npm plugins in the extension host. Clearly report installed plugin configurations as unsupported rather than silently claiming they loaded.
- Retain Kilo permission prompts and workspace path checks. Do not claim OS-level process isolation; remove/disable the current optional sandbox behavior and expose that security change clearly.
- Start with a fresh extension-owned runtime store. Do not migrate old sessions or provider credentials from `globalStorage/kilo-cli`; leave the old directory untouched and require users to reconnect providers.
- Do not add dependencies. Remove CLI-specific runtime/build dependencies and SDK client usage; use extension-owned runtime contracts and types.

## Implementation Sequence

1. **Inventory the current extension contract.** Enumerate all `KiloClient` methods and events used by `KiloProvider`, Agent Manager, settings, marketplace, browser automation, telemetry, and commands. Map each to an in-process runtime capability, a direct Kilo/provider network call, or an explicitly excluded feature. Preserve existing webview message contracts and directory/worktree scoping. Use the inventory as the parity checklist.
2. **Define extension-owned runtime contracts and state.** Add a Kilo-owned `NativeRuntime` composition boundary and runtime types for sessions, messages/parts, providers, events, permissions, questions, MCP, config, and status. Implement versioned local storage under extension `globalStorage` using Node filesystem APIs and crash-safe atomic writes; retain per-directory/worktree isolation and multi-window behavior. No import or runtime dependency on the generated SDK client should remain.
3. **Implement provider and auth runtime.** Implement a cancellable streaming request loop with `fetch`, SSE parsing, normalized usage/errors, tool-call and reasoning translation, timeout/retry behavior, and provider-specific request formats. Cover every built-in provider/auth flow found in the inventory, Kilo Gateway, and custom OpenAI-compatible endpoints. Store secrets in VS Code `SecretStorage`; preserve cloud/device and OAuth flows through their existing network endpoints. Do not dynamically install or load provider packages.
4. **Implement the agent/session engine.** Build session lifecycle, durable message/part writes, prompt assembly, streaming events, resume/fork/abort/revert/compact, model selection, context limits, error handling, and task/subagent orchestration. Keep event ordering and UI-visible event semantics compatible with current sidebar, open-tab, and Agent Manager consumers. All long-running work must be async and cancellable so the single extension host remains responsive.
5. **Implement built-in tools and policy.** Port the extension-needed tools to Node/VS Code APIs: read/write/edit/patch, glob/grep, shell, diagnostics/LSP, web search/fetch, question/permission handling, MCP transports, and relevant Kilo tools. Reuse existing workspace packages for indexing, memory, gateway, and UI integration where suitable. Keep permission resolution, path normalization, command approval, output truncation, and event reporting. Since OS sandboxing is explicitly out of scope, do not run untrusted plugin code and document that permission checks are not process isolation.
6. **Replace the connection transport.** Refactor the shared `KiloConnectionService` into the lifecycle/event hub for one in-process runtime shared by the sidebar, editor tabs, and Agent Manager. Preserve its subscription/filtering, status, pending-permission/question, session-completion, and directory-routing behavior. Replace SDK method calls with the local runtime facade and direct cloud service calls as appropriate. Remove `ServerManager`, HTTP/SSE-to-CLI startup/authentication, CLI health polling, and the runtime `@kilocode/sdk` client dependency. Keep existing process helpers only for user-requested tools such as shell, Git, and local MCP, not for a Kilo backend.
7. **Remove CLI packaging and size-only artifacts.** Update `script/build.ts`, `script/local-bin.ts`, snapshot/package scripts, and ignore/package rules so builds never trigger a `packages/opencode` CLI build and never copy `bin/kilo`, CLI tree-sitter/sandbox resources, or other CLI-only files. Audit `bin/ffmpeg` separately: if speech capture can use browser-native recording and supported upload formats without a new dependency, replace the FFmpeg path and remove that binary too; otherwise retain it as a separately documented VS Code feature dependency, not a CLI dependency. Retain only tree-sitter assets independently required by existing extension autocomplete. Keep extension behavior functional without CLI-derived assets.
8. **Make unsupported behavior explicit.** Hide/disable executable npm plugin operations and sandbox enablement in settings/marketplace/config flows. Surface actionable notices for existing plugin configs and explain the loss of OS-level sandbox isolation. Show provider reconnect requirements and that old CLI sessions are not migrated; do not delete old CLI data.

## Validation and Acceptance

- Unit-test provider adapters, OAuth callbacks, SSE parsing, tool-call conversion, cancellation, permissions, path containment, storage recovery/atomicity, event order, and session lifecycle. Use local HTTP fixtures or test handlers exercising the real adapter logic; do not depend on production provider credentials.
- Test representative end-to-end flows through the actual in-process runtime: create session, stream response, execute/approve a tool, persist/reopen history, abort, MCP call, and run parallel Agent Manager worktree sessions.
- Add regression coverage for provider/config UI behavior, Kilo cloud features, indexing/search, speech-to-text (if FFmpeg is removed), and existing webview event/message contracts.
- Run VS Code package typecheck, lint, unit tests, and production build/package checks. Exercise Linux, macOS, and Windows-sensitive paths, especially shell spawning, credentials, OAuth redirects, microphone capture, and file storage.
- Build a VSIX and inspect its archive: assert there is no `bin/kilo`, `kilo.exe`, CLI build artifact, or CLI backend launcher path. Report compressed VSIX total plus compressed/uncompressed top-level and largest-file breakdown. Compare against the current 182 MB artifact and identify any remaining native helper binaries.
- Release only after the CLI-free VSIX passes the parity checklist. Ship release notes calling out fresh local state, provider reconnection, dropped executable plugins, and the lack of OS-level sandbox isolation. Do not ship a dual CLI/fallback build; rollback uses a previously published VSIX.

## Main Risks

- This replaces the runtime, not merely a packaging artifact. The extension currently relies on many backend endpoints and event semantics, so the inventory and parity checklist must be exhaustive before deleting the transport.
- Provider-native protocol and OAuth parity is a large surface. The provider matrix must be tested independently, and unsupported cases must fail clearly rather than falling through to the wrong protocol.
- Extension-host execution removes the process boundary. Permission/path checks cannot stop a compromised tool or arbitrary shell command from accessing resources available to the extension host.
- Moving runtime work into one host can affect responsiveness and memory under concurrent Agent Manager sessions. Streaming, tool output, indexing, and persistence must avoid synchronous/blocking work and uncontrolled buffering.
- The extension package already includes workspace runtime packages and type-only SDK usages across many files. Ensure no accidental CLI SDK client, generated server contract runtime, CLI resource copy, or transitive CLI build remains in the packaged artifact.
